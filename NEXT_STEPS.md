## Backend additions for staff management
- `users` table gained `active` and `token_version` columns (auto-migrated for existing DBs).
- New `requireAuth()` helper in `utils.dart` cross-checks the JWT against current DB state (active + token version) on every request — not just new routes — so a deactivated account or a forced logout takes effect immediately instead of waiting for the JWT to expire. `menu_routes.dart` / `order_routes.dart` were switched to use it too.
- Owner cannot deactivate or delete their own account (guarded server-side).
- Verified via curl (login/create/list/deactivate/reactivate/force-logout/self-protection) and via real widget tests driven against a live local server instance (throwaway test, not committed).

## Done so far — Kitchen Display System (screen 15)
- **Kitchen Display** — live 3-column kanban board (New / Preparing / Ready) fed by a WebSocket (`ws://<host>/ws/kitchen`, JWT passed as a query param since browsers can't set custom headers on the WS handshake). Connects on screen open, auto-reconnects with a 3s backoff on drop, shows a Live/Connecting/Reconnecting/Offline badge.
- Orders carry a kitchen `status`: pending → preparing → ready → completed. New orders start `pending`; cashiers don't see or set this — it's purely the kitchen's view. Advancing a card's status PATCHes the server, which broadcasts the change to every connected display; a card marked "Complete" drops off the board (server only returns non-completed orders in the initial snapshot).
- Cards flag as urgent (red border) once they've been waiting 5+ minutes without being marked ready.
- Wired into the sidebar (desktop) and mobile popup menu for all roles — kitchen staff are often workers, so this one isn't owner-gated like Staff Management.
- Verified two ways: a standalone Dart script exercising the raw WebSocket protocol directly against the live server (snapshot delivery + live `order_created`/`order_status` broadcasts, unambiguous pass), and a widget test driving the actual screen end-to-end (order appears live, all three status-transition taps PATCH and re-render correctly, card disappears on completion). The widget test isn't committed — its final cleanup step trips an unrelated `flutter test` harness limitation (`dart:io` WebSocket close creates a real timeout timer that the fake-clock test binding can't resolve), not an app defect.

## Backend additions for Kitchen Display
- `orders` table gained a `status` column (auto-migrated; historical rows default to `completed`, new orders always insert explicit `pending`).
- New `KitchenHub` (`server/lib/kitchen_hub.dart`) fans out `order_created`/`order_status` events to all connected sockets and sends a fresh snapshot of active (non-completed) orders to each new connection.
- New `GET /ws/kitchen?token=<jwt>` route (`kitchen_routes.dart`) and `PATCH /orders/:id/status` route; both reuse the same active/token-version DB check as `requireAuth` (refactored into a shared `verifyToken` so the query-param path and the header path share logic).

## Done so far — Role-based access control, Role Selection & Customer Display (screens 20–21)
- **Real RBAC** — Employee/Manager/Owner are no longer cosmetic. Server: `requireRoles()` (`server/lib/utils.dart`) gates the four menu write routes (create/update/delete/toggle) to owner+manager; menu reads and all order routes stay open to any authenticated role (employees need them for order taking/history). Client: `ServerClient.canManageShop` gates Menu Management and Reports out of the sidebar/popup/bottom-nav for employees, and both screens also self-guard (`AccessRestrictedScreen`) if reached directly. Staff Management stays owner-only as before. "worker" is still the DB/JWT value (no migration) but now displays as "Employee" everywhere in the UI.
- **Role Selection screen** (screen 21) — new front door for any device joining as a client (`features/role_select/role_selection_screen.dart`), reached from Welcome's "Connect to Server". Picks a `DevicePurpose` (Cashier/Manager, Kitchen Display, or Customer Display) that's threaded through `ConnectScreen` → `LoginScreen`: Cashier/Manager is the existing flow into the hub; Kitchen Display signs in and lands directly on `KitchenDisplayScreen(standalone: true)` (which gained its own logout icon since there's no hub to sign out from); Customer Display skips login entirely.
- **Customer-facing display** (screen 20) — `features/customer_display/`. Backend: `CustomerDisplayHub` (`server/lib/customer_display_hub.dart`) is a pure relay over `GET /ws/customer-display` — no auth, cart contents aren't sensitive and it's LAN-only — that forwards whatever one connected client sends to every other connected client. `CustomerDisplayService` mirrors `KitchenService`'s connect/reconnect pattern with a 2-message protocol (`cart`, `thank_you`; empty cart items reads as idle). `OrderTakingScreen` publishes the live cart on every mutation; `PaymentScreen` publishes a thank-you (total + change) on payment confirm. `CustomerDisplayScreen` is a full-screen kiosk view (idle/live-cart/thank-you) with a confirm-gated exit.

## Done so far — Item-level kitchen tracking, real Thai i18n, real thermal printing
- **Item-level kitchen prep tracking** — `order_items` gained a `status` column (`pending`/`preparing`/`ready`, auto-migrated). `AppDb.updateOrderItemStatus` updates one item and re-derives the parent order's own status from all its items (order goes `preparing` once any item does, `ready` once every item is; `completed` stays an explicit order-level-only action). New `PATCH /orders/:id/items/:itemId/status` route broadcasts both a new `item_status` WS event and the existing `order_status` event via `KitchenHub`. `KitchenDisplayScreen` now shows a tappable status chip per item on each card instead of one whole-order action button; the "Complete" button only appears once every item reads `ready`.
- **Real Thai/English i18n** — standard Flutter `flutter_localizations` + generated `AppLocalizations` (from `lib/l10n/app_en.arb` / `app_th.arb`, ~180 keys covering every screen in the app). New `LocaleController` (`core/services/locale_controller.dart`) drives `MaterialApp.locale` live — `main.dart` sets the initial locale from the persisted `AppSettingsService` language before `runApp`, and Settings' language picker updates it immediately, no restart needed. `home_placeholder_screen.dart`'s hand-rolled weekday/month abbreviations were replaced with `intl`'s `DateFormat` (locale-aware for free) rather than being ARB-ified string-by-string.
- **Real thermal printing** — `PrinterService` (`features/cashier/services/printer_service.dart`) uses `package:unified_esc_pos_printer` (real ESC/POS transport covering both `PrinterChoice` options: Bluetooth Classic/BLE and USB, the latter via the Windows Print Spooler or Android USB-OTG). Scans for a printer matching the Settings choice, connects to the first match, builds a real `Ticket` (header, order #/date/payment method, itemized lines via `ticket.row()`, total, cash/change, cut), prints, disconnects. Receipt screen's PRINT button is wired to it for real, with a loading spinner and a real success/no-printer/error SnackBar.
  - **Caveat**: this compiles against and exercises the real package API (verified by reading the package source directly, not just docs) and passes `flutter analyze`, but there's no physical Bluetooth/USB thermal printer in this environment to test an actual print job against — best-effort, hardware-unverified.

## Done so far — Bundle/launch the server from the app (Windows host)
- Decision (user-confirmed): the server runs as a **detached background process**, not a child process tied to the app's lifecycle. Rationale — the Windows host machine is often also a cashier terminal; if the server died with the app, closing the POS window would drop every other connected device (kitchen display, customer display, other cashiers) with no warning. A Windows-service install was considered but is out of scope (needs a real installer).
- New `LocalServerLauncher` (`pos/lib/core/services/local_server_launcher.dart`): `ensureRunning()` health-checks `GET http://127.0.0.1:8080/health`; if unreachable, looks for a bundled `server\minepos_server.exe` next to the app's own executable (`Platform.resolvedExecutable`'s parent dir) and launches it via `Process.start(..., mode: ProcessStartMode.detached)`, then polls health until it responds or times out. No-op on non-Windows (self-hosting is Windows-only, same constraint as `ConnectionModeStep`). In dev (`flutter run`), the bundled exe doesn't exist, so this is a safe no-op — the old manual `dart run bin/server.dart` workflow is untouched.
- Wired into two places: **Create Shop wizard** (Local mode's `_finish()` now calls `ensureRunning()` before `/setup` instead of assuming the server is already up) and **Welcome screen's "OPEN REGISTER"** button (previously dead code — it pushed `LoginScreen` without ever setting `ServerClient.baseUrl`, so login always failed; now on Windows it calls `ensureRunning()`, sets `baseUrl = '127.0.0.1:8080'` on success, or shows an error pointing at "Connect to Server" on failure). Non-Windows platforms keep the previous "Open Register" behavior untouched (that's a separate pre-existing gap, not this session's scope).
- New `pos/tool/build_windows_release.ps1`: compiles `server/bin/server.dart` via `dart compile exe`, runs `flutter build windows --release`, and copies the resulting `minepos_server.exe` into `build/windows/x64/runner/Release/server/` so `LocalServerLauncher` finds it at runtime. Verified `dart compile exe` succeeds for the server entrypoint in this environment (compiled a throwaway copy, deleted it — not committed).
- **Caveat**: the bundled server still needs `sqlite3.dll` reachable at runtime (same pre-existing requirement as running it manually) — the release script doesn't bundle that DLL yet, so a from-scratch install still needs it dropped in next to `minepos_server.exe` or on PATH. Not fixed this session.
- Not verified live end-to-end (would need an actual Windows release build + a second device on the LAN, neither available in this environment) — verified via `flutter analyze`/`dart analyze` (both clean) and the `dart compile exe` sanity check above.

## Done so far — Remove Shop (Settings, owner-only)
- Backend: `AppDb.wipeShop()` (`server/lib/database.dart`) deletes every row from every table — users, menu, orders/order_items, otp_tokens, shop_config — resetting the server to the same pristine pre-`/setup` state (so a new shop can be bootstrapped again, same as a from-scratch install). New `DELETE /shop` (`server/lib/routes/shop_routes.dart`, registered in `bin/server.dart`): owner-only JWT check, then requires the request body's `email` to match `shop_config.email` (the shop's own registered contact email — the `users` table has no email column, only `shop_config` does), `username` to match the acting owner's own username, **and** `password` to match their password hash, before wiping. Deleting the owner's row mid-request means their JWT stops verifying on the very next call, since `verifyToken` looks the user up by username every time — no separate token-invalidation step needed.
- Client: new `ShopService` (`pos/lib/features/manager/services/shop_service.dart`), same request/error-handling shape as `StaffService`. Settings screen (`features/manager/settings_screen.dart`) gained an owner-only "DANGER ZONE" section with a "REMOVE SHOP" button that opens a bottom sheet (`_RemoveShopSheet`) requiring the shop's email + the owner's own username (hint text shows the signed-in username) + their password, matching the confirm/cancel/loading pattern used by Staff Management's add-staff sheet. On success, clears the session and returns to Welcome, same as Disconnect.
- Verified live end-to-end against two throwaway server instances on separate ports/data dirs (never the real dev DB, which already had the user's own test shop on it): `/setup` → login → delete rejected with wrong email → rejected with missing username → rejected with wrong username → rejected with wrong password → succeeds with all three correct → `/setup` works again afterward (proving the wipe) → the pre-delete JWT is immediately rejected on the next request. Both throwaway instances and their data dirs were torn down after.

## Done so far — Noto Sans Thai everywhere (not just the Thai locale)
- Originally scoped as Thai-only, then extended app-wide once confirmed Noto Sans Thai's glyph coverage includes Latin + Latin Extended alongside Thai (per Google Fonts' own specimen page). `AppTheme.light` (`pos/lib/core/theme/app_theme.dart`) now always uses `GoogleFonts.notoSansThai`/`notoSansThaiTextTheme()` — base `textTheme`, `headlineMedium`, both button themes — replacing Quicksand/Montserrat entirely, so English and Thai screens share one typeface instead of visibly changing fonts when the language is switched.
- Still takes the active `Locale` for one thing: `headlineMedium`'s letter-spacing (4px in Latin branding like "MINEPOS", 0 for Thai, since wide Latin-style tracking distorts Thai vowel/tone-mark shaping) — that style is also used for translated Thai screen titles (login, forgot-password, OTP, reset-password), not just the untranslated brand title, so it has to stay locale-aware even though the font family no longer is.
- `main.dart` builds the theme from `LocaleController.instance.locale`; `MinePosApp` already rebuilds on locale change, so switching language still updates spacing live, no restart needed.
- `flutter analyze` clean (confirms `GoogleFonts.notoSansThai`/`notoSansThaiTextTheme` exist in the pinned `google_fonts: ^6.2.1`), no test regressions. No more `GoogleFonts.quicksand`/`montserrat` references anywhere in the app.

## Fixed — "widget has been unmounted" crash on real login
- Reported live by the user (not caught by the widget tests, which mock the network layer). `LoginScreen._signIn()` (`pos/lib/features/auth/login_screen.dart`) called `Navigator.of(context).pushAndRemoveUntil(MaterialPageRoute(builder: (_) => ... AppLocalizations.of(context)!.loginWelcomeMessage))` — the builder's own context parameter was discarded as `_`, so `AppLocalizations.of(context)` inside it closed over the outer `_LoginScreenState`'s context instead. `pushAndRemoveUntil` removes the login route as part of the same transaction, so by the time the new route's builder actually ran, that state was already unmounted, crashing every real (non-mocked) sign-in. Fixed by resolving the localized string into a local variable *before* calling `Navigator`, while `context` was still guaranteed valid — the builder closure now only touches that captured string, not `context`.
- Audited every other `builder: (_) =>` route callback in the app for the same shape (grepped for `AppLocalizations.of(context)` inside a discarded-context builder). Found and fixed one more of the same pattern in `welcome_screen.dart`'s `_openRegister()` (written this session) — lower risk since it uses `push` not `pushAndRemoveUntil` (the underlying route isn't removed, so its state stays mounted), but fixed for consistency/safety anyway. `create_shop_screen.dart`'s similar-looking builder is safe as-is — it reads off an `AppLocalizations` instance already captured in a local (`l10n`) before any `await`, not a fresh `.of(context)` call inside the closure.
- Verified via `flutter analyze` (clean) and `flutter test` (same 3 pre-existing network-dependent failures, no new ones — these tests don't exercise real navigation far enough to have caught this in the first place).
